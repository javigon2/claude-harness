**Harness UI evaluation — 2026-10-22**

The harness is a working functional prototype with a recognizable office concept. Its strongest parts are the planner-to-run workflow, local deployment, explicit server state, and testable fake mode. Its biggest product gap is supervision: understanding outcomes, reviewing evidence, and recovering from failure still requires interpreting a technical table and often returning to the terminal.

Keep the office concept, but make it an interactive overview above a clear project status and task inspector. Prioritize truthful outcomes and stable interaction before adding more visual detail.

Evaluation covered commit `9bd8063`, the UI implementation and adjacent runner code, and headless Chrome at 1440 × 1000 and 390 × 844. A scratch git repository ran the real UI with the demo planner and fake workers. Browser clicks exercised description → questions → plan → implementation → completion; fixtures covered blocked and paused runs. No real model was called, so this evaluation does not establish real-agent output quality or real-world execution latency. The selected page and office HTTP end-to-end tests passed: **36 tests**.

**What is already good**

- The office makes parallel work recognizable, and status colors are consistent with table badges. Preserve that identity.
- The happy path works through the browser, including automatic selection of the launched run and the offer to plan the next stage.
- Native controls, a native dialog, keyboard activation of the planner, and text-based Markdown rendering provide a useful foundation.
- The server keeps mutations constrained: loopback binding, Host and Origin checks, a per-server token, bounded JSON bodies, and state guards.
- Fake mode is particularly valuable: it supports repeatable demos and interaction tests without model cost.
- A small self-contained UI suits this local tool. The findings do not justify a framework migration.

**Priority 1: distinguish completion from success**

The blocked fixture has three blocked tasks and no successful task, yet the header displays a green `finished` badge and no warning banner. The event feed contains the true outcome, but the most prominent signal implies success.

There is a related progression issue: `next_stage_of()` checks that the previous run finished, without checking whether its tasks succeeded. An isolated reproduction with an approved two-stage plan and the all-blocked run returned stage 2.

Recommended behavior:

- Separate lifecycle (`running`, `ended`) from outcome (`succeeded`, `needs attention`, `paused`, `stopped at budget`).
- Show a plain-language summary such as **“0 of 3 tasks completed · 1 root failure · 2 tasks blocked by dependencies.”**
- Default to recovery when prerequisite work is incomplete. Any explicit override to proceed should explain what is missing.
- Reserve green for a successful outcome and show the next useful action beside every non-success outcome.

Evidence: `src/harness/ui/view.py:285–290`, `src/harness/ui/office.py:135–160`, and the blocked browser walkthrough. This is the highest-priority correctness change.

**Priority 2: preserve interaction during live updates**

Opening a failure's `details` disclosure and waiting for the next 15-second heartbeat closes it. Focusing the actual interactive planner desk also loses keyboard focus to `BODY` after that heartbeat. `render()` rebuilds the task rows and office desks even when the underlying completed run has not changed.

Update existing elements by task ID; only replace regions whose data changed. Preserve disclosure state, focus, selection, and scroll position. A heartbeat should update connection freshness without rebuilding the page. Also preserve the run picker rather than replacing its options every two seconds when the run list is unchanged.

Treat these as behavioral requirements: an expanded failure stays expanded until the user closes it; keyboard focus survives background updates.

Evidence: `src/harness/ui/static/index.html:578–612,652–660`; `src/harness/ui/server.py:353–387`; browser reproductions.

**Priority 3: make launch quality and consequences visible**

The UI's `run_argv()` omits `--review`, while the CLI defaults that option to false. Runs launched from this page therefore use acceptance/diff checks without the optional model reviewer. This may be a sensible cost choice, but users cannot see or change it in the page.

Add a compact launch summary showing the selected stage, review mode, maximum parallel workers, budget policy, target repository/branch, and automatic merge behavior. Offer a small number of explicit settings rather than exposing arbitrary CLI arguments. Display exactly which checks ran in the resulting task evidence.

The label **“Plan next stage”** also understates its effect: the backend plans the stage and then launches its run. Either label that action **“Plan and run stage 2”**, with its settings visible, or provide an actual review step between planning and execution.

Evidence: `src/harness/ui/office.py:657–670,773–783`, `src/harness/cli.py:118–122`, and `src/harness/ui/static/index.html:519–529`.

**Priority 4: make the first screen self-explanatory**

The empty screen currently contains only a planner illustration and “No runs yet.” The header is hidden. A new user must discover that the illustration opens the principal workflow.

Keep a persistent project header with project name, repository/branch, connection state, and a visible **“Start planning”** action. Add a short explanation: “Describe a change, review the plan, then follow its implementation.” Show demo/read-only mode explicitly. The illustration can remain a second way to reach the planner.

Once work exists, prioritize status counters and actions over raw IDs and tier accounting. For example: **“Stage 1 · 2/8 complete · 3 active · 1 needs attention.”** Show task names on desks and reserve IDs/model details for secondary text.

**Priority 5: turn desks into useful task entry points**

Worker desks currently repeat task IDs and tiers, with no drill-down. Their activity bubbles truncate at a narrow width, and completed/blocked desks rely on color unless the user consults the table.

Make each desk or task row open an inspector with:

- Task goal, status text, current activity, elapsed time, and dependencies.
- Attempt history with model, cost, and the reason for escalation.
- Acceptance command results, review verdict when enabled, and merge/commit evidence.
- A short failure explanation and the next available recovery action.

Distinguish a root failure from downstream tasks waiting on it. Start with a simple “blocked by” link; a full dependency graph can wait.

These are currently task stations, one per task, rather than a representation of the active worker pool. Make that distinction clear when showing parallelism. At larger task counts, group desks by wave/status and collapse completed groups. A compact list view should remain available.

**Priority 6: improve recovery and connection feedback**

Before a run exists, there is no run EventSource. Failed office/run polling is silently ignored. In a browser offline check with no runs, the page showed no connection warning after polling failed. A user can therefore mistake stale planner state for live work.

Track request success, last successful update, and reconnecting state for the whole application. Preserve the last data while clearly marking it stale. Handle HTTP errors as well as network failures.

The paused-run banner currently supplies `harness run <plan> --repo <repo> --resume`, which requires manual substitution. First provide a copyable command with the actual selected run ID and paths, properly quoted. The run ID matters when inspecting an older run. Later add validated server actions for resume/retry and “stop after current attempts”; an immediate stop needs defined worker and worktree cleanup semantics.

The plan fetch also lacks visible loading/failure feedback: `/api/plan` responses are parsed without checking HTTP status and network errors are swallowed. Show a retryable error, identify the displayed plan revision, and make stale plan content explicit before approval.

**Priority 7: strengthen visual hierarchy and accessibility**

The layout is readable on desktop but looks like an internal diagnostic page. The dense full-width table and event list compete with the office, while primary and secondary modal actions look nearly identical.

Use a restrained spacing/type scale, distinct primary buttons, and grouped project/run summaries. Keep task status and the next action visible; move tokens and per-tier cost detail behind an inspector or expandable breakdown. Default the event feed to important transitions, with filters for task and event type.

The long plan lives inside an independently scrolling area inside a scrolling modal. A persistent planner panel or dedicated planning view would accommodate conversation history and document review more comfortably. A short modal remains suitable for confirmations.

At 390 px viewport width the page's content measured **500 px** wide, with the task table around **484 px**. Use responsive task cards or a contained horizontal table scroller; avoid scrolling the entire page sideways.

Complete the accessibility foundations: visible labels for answer/change textareas, text status on desks, deliberate focus movement when a question appears, restrained live announcements for important status changes, and a reduced-motion alternative to the infinitely flashing ready desk. Do not announce every streamed tool event.

Evidence: `src/harness/ui/static/index.html:46–75,98–186` and browser screenshots.

**Priority 8: reduce repeated work as history grows**

Each tab polls office state once per second and the run list every two seconds: roughly **90 HTTP requests per minute**, plus its run SSE connection. Run SSE checks file signatures every 0.5 seconds and rebuilds a complete snapshot on changes and 15-second heartbeats. `build_view()` reads/parses the whole event log before selecting the last 50 feed events.

A local synthetic probe added progress events to the existing running fixture and timed five view builds per size:

| Added events | Event file size | Median `build_view()` time |
|---:|---:|---:|
| 100 | 17 KB | 0.71 ms |
| 10,000 | 1.45 MB | 25.84 ms |
| 50,000 | 7.25 MB | 134.88 ms |

These are warm local measurements for a small task set, not production latency estimates. They demonstrate work growing with total history even though the visible feed is bounded.

Cache parsed plans, planner replies, and run views using file/version signatures; share cached snapshots across clients. Incrementally process appended events when volume warrants it, handling truncation/replacement correctly. Reuse data snapshots on heartbeats, update only freshness, and slow polling for hidden or completed views. If office updates move to SSE, multiplex them with run state to avoid unnecessary simultaneous streams.

Fix the DOM replacement issue first; it already affects users at tiny scale. More elaborate event storage or virtualization should follow measured need.

Evidence: `src/harness/ui/view.py:188–237,301–325`, `src/harness/ui/server.py:365–387`, `src/harness/ui/office.py:480–508`, `src/harness/ui/static/index.html:562–565,664–682`.

**Ideas with useful upside**

| Idea | User benefit | Priority |
|---|---|---|
| Attention queue | One place for planner questions, failed checks, rate limits, and budget stops; each item opens the relevant action. | High |
| Completion receipt | See changed files, executed checks, review status, merge result, and remaining issues without reading raw events. | High |
| Plan revision comparison | Understand what changed after asking the planner for revisions before approving. | Medium |
| Total project cost | Separate planner, worker, and reviewer cost, with totals across stages and the configured budget. | Medium |
| Efficiency trends | Compare first-attempt success, retries, escalation rate, elapsed time, and cost per successfully merged task. | Medium |
| Stage timeline | Show completed, current, and future stages, with the dependency that prevents progression. | Medium |
| More office animation/customization | Adds personality, but little immediate benefit to completing or supervising work. | Low |

Cost should be labeled as an estimate where appropriate. The current cap stops new attempts after booked cost exceeds it; already-running attempts can finish and overshoot it. It is not a hard total-spend guarantee, and the UI's run total is separate from planner cost.

**Suggested order of work**

1. Correct outcome/progression semantics, preserve interaction through updates, and expose connection/plan-load failures.
2. Add project identity and an obvious start action, honest launch settings, and task inspection with evidence.
3. Improve layout, keyboard/focus behavior, responsive presentation, and planner history/review.
4. Cache repeated computations, then add cost and success-rate insights after gathering representative runs.

Use a small browser regression suite for the cases observed here: blocked outcomes, next-stage gating, disclosures/focus through heartbeats, offline-before-first-run, failed plan loading, and narrow viewport layout. Existing page tests largely check source structure, syntax, or stubbed DOM behavior; the office end-to-end tests exercise HTTP rather than browser interaction.

The next iteration succeeds when a user can identify the project, understand whether its work succeeded, inspect the evidence, and take the next useful action without reconstructing the story from the event feed.
